§ 01

Thesis

Enterprise MCP adoption fails when teams bolt identity onto per-server implementations. The working model inverts that assumption: identity, policy, and content inspection concentrate at a single gateway; individual MCP servers become thin resource providers; a registry governs what code is allowed to run at all.

Two agent estates — build on enterprise compute, buy on SaaS — must reach the same tool catalog through the same choke point, with the controls scaled to who owns the execution environment.
PRINCIPLE 01
Gateway is the only enforcement point.
MCP servers never authorize calls themselves. All policy, identity, and content decisions happen before a server is reached.
PRINCIPLE 02
Registry is the only trust anchor.
If a server, a version, or a manifest is not in the registry with a valid signature, the gateway refuses to route to it. No exceptions at runtime.
PRINCIPLE 03
Trust scales with execution locus.
Buy agents expose a strictly reduced tool surface, with tighter rate limits, lower data classifications, and network-pinned ingress. Build and buy are not equal.
§ 01.5

What changed in 2026 · landscape & threats

This document was rebaselined against current spec and threat reality (April 2026). Five things shifted the architecture; one stayed exactly where it was.

GOVERNANCE
MCP donated to the Linux Foundation
In December 2025, MCP was donated to the Agentic AI Foundation (AAIF), a directed fund under the Linux Foundation co-founded by Anthropic, Block, and OpenAI with support from Google, Microsoft, AWS, Cloudflare, and Bloomberg. SEPs (Specification Enhancement Proposals) now move through formal Working Groups. Vendor-neutrality is no longer aspirational — it is structural.
AUTHORIZATION
RFC 9728 + DPoP are now table stakes
RFC 9728 Protected Resource Metadata (April 2025) is the discovery anchor: every MCP server publishes /.well-known/oauth-protected-resource declaring its AS, scopes, and DPoP requirements. DPoP (RFC 9449) sender-constrained tokens are signaled via dpop_bound_access_tokens_required. The 2025-11-25 spec adds OIDC Discovery 1.0 and de-emphasizes Dynamic Client Registration in favor of pre-registered clients or SEP-991 Client ID Metadata Documents.
USER INTERACTION
Elicitation · URL mode is mandatory for secrets
The 2025-11-25 spec introduces elicitation: servers can ask users for input mid-session. Two modes: Form mode (structured data, JSON Schema validated) and URL mode (browser redirect for sensitive flows). Form mode MUST NOT be used for passwords, API keys, tokens, or payment credentials — those MUST use URL mode so credentials never transit through the MCP client.
TOOL METADATA
Tool + security annotations are policy-grade signals
Tool annotations (readOnlyHint, destructiveHint, idempotentHint, openWorldHint) are stable and adopted by Azure DevOps, GitHub, and others. SEP-1075 Security Annotations adds read_confidentiality, write_confidentiality, and integrity as lattice labels for information-flow control. Both feed the PDP as policy inputs.
THREAT REALITY
First malicious MCP servers are in the wild
postmark-mcp — first confirmed malicious MCP server, silently BCC'd every outgoing email to an attacker-controlled address for weeks before detection. Trend Micro found 492 exposed MCP servers with zero authentication in early 2026. OWASP MCP Top 10:2025 now formalized (MCP01–MCP10); OWASP Agentic AI Top 10 released December 2025; CoSAI MCP Security document approved January 2026 with 12 threat categories.
UNCHANGED
The architecture conclusion holds
Despite all of the above, the structural answer is the same: centralize at a gateway, anchor trust in a registry, isolate clients per server, scale controls with execution locus. The 2026 updates make the gateway's job richer — PRM enforcement, DPoP support, elicitation routing, annotation-driven policy — but they do not move the chokepoint.
§ 02

Trust zones & legend

The architecture has three concentric trust zones separated by hard network and identity boundaries. Nothing crosses a boundary without a signed, scoped, audited credential.

Zone A · Untrusted

SaaS / PaaS hosts running buy agents. Anthropic, OpenAI, GitHub, Microsoft. Enterprise has zero runtime visibility. Controlled only at the network edge and by contract.

Zone B · Perimeter / DMZ

Dedicated ingress hostname for agent traffic. WAF, mTLS termination, IP allow-list restricted to approved SaaS egress ranges. No direct path into the enterprise zone.

Zone C · Enterprise

Build agents, model garden, MCP gateway, registry, AS, PDP, federated MCP servers. Sandboxed servers with no east-west reachability; all traffic observed.

Control plane

Registry, AS, PDP. Out-of-band from data plane; reachable only by the gateway. Independently scaled and backed up — the integrity of the system depends on this tier.

§ 03

Reference architecture

The canonical view. Data plane in cyan, control plane in violet, trust boundaries as dashed envelopes. Both build and buy estates converge on the MCP Gateway.

On the two gateways. The Enterprise API Gateway is your existing platform investment (Kong, Apigee, APIM, AWS API GW). It handles routing, coarse authentication, metering, and general API concerns for all enterprise HTTP traffic. The MCP Gateway sits behind it and is MCP-protocol-aware: it speaks JSON-RPC, understands tool schemas, does token exchange, enforces the registry, and runs the prompt-injection scanners. They can be collapsed into one if (and only if) your API gateway speaks MCP natively — most don't yet.

On the IDP / AS. The Authorization Server (component of your enterprise IDP: Entra, Okta, Keycloak, Ping) issues user tokens via OAuth 2.1 + PKCE and performs token exchange (RFC 8693) for the MCP Gateway. It is the trust anchor for who; the Registry is the trust anchor for what. Both build and buy agents federate here — no separate identity store for SaaS users.

§ 03.2

MCP Host & Client · internals and in-process controls

The gateway cannot see what happens inside the agent process — consent decisions, credential storage, context assembly, sampling requests, and user-visible tool descriptions all live there. These controls must be implemented in the Host/Client code itself. Skip them and the gateway is defending a compromised decision.

The Host owns the LLM loop, user consent, and credential vault. The Client is a per-server connector with a 1:1 session. One server → one client is the isolation invariant that prevents cross-server context bleed.
mcp-gateway.corp.example.com · arbitrary MCP endpoints blocked at OS egress + host firewall · Bearer token = short-lived user JWT from enterprise IDP · client certificate presented for mTLS (per-workstation or per-workload cert) · JSON-RPC payload signed for replay detection · request_id included for SIEM correlation (see LOG-03) prompt + consent scoped token mTLS · gRPC tool-call intent → MCP Gateway (T4 in §03) H1 H2 H3 H4 H5 All host internals run inside a single OS process · one trust boundary · one credential context For buy agents (Copilot / ChatGPT), this entire process runs on the SaaS vendor's infrastructure — enterprise has no code-level control, only contract + network edge

⚠ BUY-AGENT CAVEAT
For buy agents (Copilot, ChatGPT, Gemini), the Host/Client runs inside the SaaS vendor's infrastructure. You cannot implement the HOST-* controls yourself. Instead you require them via: vendor security attestations (SOC 2 Type II, ISO 27001, vendor-specific AI-system questionnaires), DPAs referencing specific controls, and, where the vendor exposes them, configuration toggles (e.g. Copilot tenant admin settings for MCP). Where a vendor's implementation is weaker than your build-agent bar, the gap is compensated by the stricter tool surface, rate limits, data classification ceiling, and response redaction you apply at the gateway — not by assuming parity.

§ 06

MCP Gateway · chokepoint specification

The gateway is a reverse proxy that happens to understand MCP. Every responsibility below is non-negotiable and must be implemented before production MCP traffic is enabled.

⚠ DESIGN CONSTRAINT
The gateway fails closed. Registry unreachable → deny. PDP unreachable → deny. DLP scanner unreachable → deny. PRM document unreachable → deny. Uptime is achieved via redundancy of the control plane, not by loosening the gateway when components are sick. If the registry is down, nothing runs — that is the correct behavior.

§ 09

Residual risks

What the controls don't fix. Documenting these is part of honest design — operators must not assume the architecture is complete defense.

Prompt injection is mitigated, not solved.
Detection rates on adversarial payloads remain imperfect; rely on egress DLP and least-privilege rather than on detection alone. Pair with human-in-the-loop for destructive tools (now signaled by destructiveHint annotation).
SaaS runtime is opaque to the enterprise.
You cannot verify what Copilot, ChatGPT, or Gemini actually does with data post-ingress. Rely on contract (DPA, sub-processor transparency), not inspection. Network edge + token scope are the only enforceable controls. AAIF/LF governance helps with vendor neutrality but not with runtime opacity.
Natural-language exfil bypasses schema.
Tools that return free-text responses can carry arbitrary content the schema firewall can't constrain. structuredContent output schemas (OUT-06) close most of this; legacy free-text tools remain a residual gap.
Registry integrity depends on the signing chain.
Fulcio / Sigstore outages or key compromise degrade assurance across all servers. Mirror transparency logs; plan for signing-root-compromise tabletop. Reverse-DNS namespace auth (SUP-09) reduces but does not eliminate impersonation risk.
PDP latency is a DoS pressure point.
Policy cache poisoning or latency injection can pressure operators to fail-open. Constraint: gateway must fail-closed, period. Handle availability with PDP redundancy, not policy relaxation.
LLM reasoning is not auditable like policy is.
You can prove a tool call was allowed; proving why the model chose to call it is weaker. Capture tool-intent traces alongside decisions for post-hoc review.
Malicious published servers are now in-the-wild (2026).
postmark-mcp demonstrated the threat: a published, registry-listed server that quietly exfiltrated email metadata for weeks. SUP-02 (signed manifests) and SUP-04 (drift detection) catch changes; they do not catch malicious-from-day-one. Mitigations: human security review on first publish (GOV-01), behavioral baselining via UEBA (LOG-04), and tool-output DLP catching unexpected egress patterns.
Cascading agent failure is not contained by the gateway alone.
A 2025 study found a single poisoned agent degraded 87% of downstream decisions within four hours in connected systems. The gateway can isolate tool calls; it cannot un-poison memory or context already shared between agents. A2A boundary enforcement (AUTHZ-10) and host-side context provenance (HOST-CTX-01) reduce blast radius but do not eliminate it.
Annotation honesty is a trust assumption.
A malicious server can mark a destructive tool readOnlyHint: true. Annotations are policy signals, not guarantees. PDP must combine annotations with empirical behavior (does this tool actually mutate state?) and registry-level review.
