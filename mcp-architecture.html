§ 01

Thesis

Enterprise MCP adoption fails when teams bolt identity onto per-server implementations. The working model inverts that assumption: identity, policy, and content inspection concentrate at a single gateway; individual MCP servers become thin resource providers; a registry governs what code is allowed to run at all.

Two agent estates — build on enterprise compute, buy on SaaS — must reach the same tool catalog through the same choke point, with the controls scaled to who owns the execution environment.
PRINCIPLE 01
Gateway is the only enforcement point.
MCP servers never authorize calls themselves. All policy, identity, and content decisions happen before a server is reached.
PRINCIPLE 02
Registry is the only trust anchor.
If a server, a version, or a manifest is not in the registry with a valid signature, the gateway refuses to route to it. No exceptions at runtime.
PRINCIPLE 03
Trust scales with execution locus.
Buy agents expose a strictly reduced tool surface, with tighter rate limits, lower data classifications, and network-pinned ingress. Build and buy are not equal.
§ 02

Trust zones & legend

The architecture has three concentric trust zones separated by hard network and identity boundaries. Nothing crosses a boundary without a signed, scoped, audited credential.

Zone A · Untrusted

SaaS / PaaS hosts running buy agents. Anthropic, OpenAI, GitHub, Microsoft. Enterprise has zero runtime visibility. Controlled only at the network edge and by contract.

Zone B · Perimeter / DMZ

Dedicated ingress hostname for agent traffic. WAF, mTLS termination, IP allow-list restricted to approved SaaS egress ranges. No direct path into the enterprise zone.

Zone C · Enterprise

Build agents, model garden, MCP gateway, registry, AS, PDP, federated MCP servers. Sandboxed servers with no east-west reachability; all traffic observed.

Control plane

Registry, AS, PDP. Out-of-band from data plane; reachable only by the gateway. Independently scaled and backed up — the integrity of the system depends on this tier.

⚠ DESIGN CONSTRAINT
The gateway fails closed. Registry unreachable → deny. PDP unreachable → deny. DLP scanner unreachable → deny. Uptime is achieved via redundancy of the control plane, not by loosening the gateway when components are sick. If the registry is down, nothing runs — that is the correct behavior.

§ 09

Residual risks

What the controls don't fix. Documenting these is part of honest design — operators must not assume the architecture is complete defense.

Prompt injection is mitigated, not solved.
Detection rates on adversarial payloads remain imperfect; rely on egress DLP and least-privilege rather than on detection alone. Pair with human-in-the-loop for destructive tools.
SaaS runtime is opaque to the enterprise.
You cannot verify what Copilot or ChatGPT actually does with data post-ingress. Rely on contract (DPA, sub-processor transparency), not inspection. Network edge + token scope are the only enforceable controls.
Natural-language exfil bypasses schema.
Tools that return free-text responses can carry arbitrary content the schema firewall can't constrain. Output DLP partially catches this; tighter output schemas are the real fix.
Registry integrity depends on the signing chain.
Fulcio / Sigstore outages or key compromise degrade assurance across all servers. Mirror transparency logs; plan for signing-root-compromise tabletop.
PDP latency is a DoS pressure point.
Policy cache poisoning or latency injection can pressure operators to fail-open. Constraint: gateway must fail-closed, period. Handle availability with PDP redundancy, not policy relaxation.
LLM reasoning is not auditable like policy is.
You can prove a tool call was allowed; proving why the model chose to call it is weaker. Capture tool-intent traces alongside decisions for post-hoc review.
