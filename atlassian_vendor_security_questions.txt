================================================================================
ATLASSIAN VENDOR SECURITY QUESTIONS
ChatGPT Enterprise + Jira SaaS via Rovo MCP Server
Prepared by: Security Architecture Team
Date: March 2026
Version: 1.0
================================================================================

CONTEXT TO OPEN THE MEETING WITH
----------------------------------
We are deploying the default Rovo MCP connector (not a custom OAuth app). Our
write-access control model uses two layers: Atlassian side via project permissions
and domain allowlist; ChatGPT Enterprise side via Manage actions with write tools
disabled. Our identity is PingFederate SAML federated to auth.atlassian.com. Every
question below refers specifically to this architecture.

================================================================================
DOMAIN 1: THE WRITE SCOPE GAP
================================================================================

Q1. SCOPE REDUCTION ON DEFAULT CONNECTOR
-----------------------------------------
The default Rovo connector OAuth token includes write:jira-work even when
ChatGPT's Manage actions has all write tools disabled. That token is stored by
OpenAI's infrastructure.

Can you, as Atlassian, configure our organization's instance of the pre-registered
OpenAI OAuth app to exclude write:jira-work from token issuance — without us
having to abandon the default connector and register a custom OAuth app? Is this
an enterprise tier configuration option, and if not, is it on your roadmap?

WHY IT MATTERS: The Manage actions control prevents ChatGPT from invoking write
MCP tools, but the token itself carries write scope. If that token were exfiltrated
or if OpenAI's infrastructure were compromised, write operations against our Jira
site would succeed. We want to know whether scope reduction is available at the
Atlassian layer so both sides enforce read-only independently.

--------------------------------------------------------------------------------

Q2. FIELD-LEVEL PERMISSION MODEL FOR editJiraIssue
----------------------------------------------------
The editJiraIssue MCP tool description says it can "update fields on an existing
Jira issue." We need the complete field-level permission model.

Specifically: can it modify the issue security level field (which controls
issue-level visibility), change the Reporter field, or update custom fields that
drive routing or access? Or is there a documented field-level blocklist enforced
by the MCP server?

WHY IT MATTERS: Your documentation says MCP respects project-level roles. That is
not the same as field-level control. A user with Edit permission who uses
editJiraIssue through MCP could potentially downgrade an issue's security level
from Restricted to None — exposing it to all Browse users — without that being
immediately obvious as a privilege escalation. We need to know whether field-level
restrictions apply or whether we need to configure field configuration schemes to
block this.

--------------------------------------------------------------------------------

Q3. ISSUE-LEVEL SECURITY SCHEME ENFORCEMENT (PRIORITY QUESTION)
-----------------------------------------------------------------
The searchJiraIssuesUsingJql and getJiraIssue tools are described as respecting
"existing project or space-level roles." Your documentation does not mention
issue-level security schemes.

Directly: does the Rovo MCP Server enforce Jira's issue security scheme — the
Security field on individual issues that restricts visibility to specific roles or
groups — or does a user with Browse Project permission see all issues in that
project regardless of their individual security level?

WHY IT MATTERS: We use issue-level security schemes to restrict certain issues
(e.g., HR, legal, executive escalations) within projects that users otherwise have
Browse access to. If MCP bypasses issue security schemes, any user with Browse
permission can read restricted issues through ChatGPT that they cannot see in the
Jira UI. This would be a direct control failure — not a configuration issue, a
product gap. This is a hard blocker for us if the answer is "project-level only."

================================================================================
DOMAIN 2: PERMISSION ENFORCEMENT IN REAL TIME
================================================================================

Q4. USER DEPROVISIONING TO TOKEN REVOCATION LATENCY (PRIORITY QUESTION)
-------------------------------------------------------------------------
We use SCIM-based provisioning through PingFederate. When we deprovision a user
in Atlassian Administration — either manually or via SCIM push — how quickly is
their OAuth refresh token invalidated?

The refresh token is held by OpenAI's infrastructure. If deactivation does not
immediately invalidate it, ChatGPT can silently exchange it for a new access token
after the user is deprovisioned. What is the actual propagation time, and is there
an API or admin action we can take to force immediate token revocation independent
of SCIM deprovisioning?

WHY IT MATTERS: This is our most likely real-world incident scenario. An employee
is terminated at 5pm, IT deactivates them in AD at 5:15pm, SCIM syncs to Atlassian
at 5:20pm. If ChatGPT can still fetch a new access token via the stored refresh
token at 5:30pm and query Jira data, we have a post-termination data access exposure
window with no current documented resolution.

--------------------------------------------------------------------------------

Q5. MAXIMUM SESSION LIFETIME VS. OAUTH REFRESH TOKEN LIFETIME
--------------------------------------------------------------
You recently released a "maximum session lifetime" control for managed accounts
(March 2026 changelog). Does this session lifetime setting apply to OAuth refresh
tokens issued to MCP clients like ChatGPT? Or does it exclusively govern browser
session cookies?

If OAuth refresh tokens are not subject to maximum session lifetime policy, we have
a situation where a browser session expires in 8 hours per our policy but ChatGPT's
MCP session remains active indefinitely via token refresh.

WHY IT MATTERS: This is a direct policy bypass gap that your own March 2026 release
may have created without accounting for MCP token lifetimes. We need a written
answer before we can tell our security team that the session lifetime control applies
consistently across all access paths.

--------------------------------------------------------------------------------

Q6. ROVO SEARCH INDEX PERMISSION LATENCY
------------------------------------------
The search:rovo:mcp scope queries Rovo's AI search index, not Jira's REST API
directly. searchJiraIssuesUsingJql hits the REST API directly. These two tools can
return different results for the same user query.

What is the maximum lag between a permission change in Jira — specifically removing
a user from a project role — and that change propagating to Rovo's search index?
Can a user whose project access was just revoked still receive results from that
project via Rovo Search before the index catches up?

WHY IT MATTERS: We cannot have two tools in the same connector with different
permission enforcement latencies. If Rovo Search is eventually consistent and JQL
search is real-time, a user whose access was revoked can still exfiltrate data via
one path while the other correctly returns nothing. This is an access control
inconsistency baked into the product architecture that needs a documented SLA.

================================================================================
DOMAIN 3: MANAGE ACTIONS — IS IT SERVER-SIDE OR CLIENT-SIDE?
================================================================================

Q7. WHERE IS MANAGE ACTIONS ENFORCEMENT BOUNDARY? (PRIORITY QUESTION)
-----------------------------------------------------------------------
ChatGPT Enterprise's Manage actions control prevents specific MCP tools from being
invoked by ChatGPT's agent. Our question is about where this is enforced.

Is it enforced server-side on OpenAI's infrastructure — so even a programmatic call
using our OAuth token cannot invoke a disabled tool — or is it enforced only in
ChatGPT's UI layer?

If a developer on our network constructed an MCP request directly using a valid
OAuth token obtained from our connector — bypassing ChatGPT entirely — would your
MCP server honor a createJiraIssue call even though we have that tool disabled in
Manage actions?

WHY IT MATTERS: If Manage actions is purely a ChatGPT UI control with no
Atlassian-side enforcement, then it provides zero protection against direct API
misuse. The only hard stop would be if write:jira-work is absent from the token —
which it is not in the default connector. We need to understand where the
enforcement boundary actually sits, because our entire read-only model depends on
this answer.

================================================================================
DOMAIN 4: AUDIT LOGS — ARE THEY USABLE FOR FORENSICS?
================================================================================

Q8. WRITE OPERATION AUDIT LOG COMPLETENESS
--------------------------------------------
When a user invokes editJiraIssue or addCommentToJiraIssue through ChatGPT, what
exactly does the Atlassian audit log entry contain?

Specifically: does it capture the full before and after field values of the edited
issue, or only the tool name, Atlassian Account ID, and timestamp? For write
operations touching production data, a "who did what" entry is insufficient for
forensics — we need the full change record to reconstruct what was altered.

WHY IT MATTERS: Your audit log documentation says it captures "tool invocations."
That language does not answer what data is in each entry. If audit logs only show
that editJiraIssue was called at 14:32 by account ID X, we cannot use them for
incident response or demonstrate compliance with our data integrity obligations.

--------------------------------------------------------------------------------

Q9. REVOCATION ATOMICITY — DOES IT KILL ACTIVE SESSIONS IMMEDIATELY?
----------------------------------------------------------------------
Audit logs in your Connected Apps list allow us to "Manage and revoke MCP app
access." When we revoke ChatGPT's MCP access from Connected Apps, is that
revocation immediate and atomic across all active user sessions — meaning all
refresh tokens ChatGPT holds for all our users are invalidated simultaneously?

Or does revocation take effect only on new token requests, leaving existing access
tokens valid until their exp claim is reached (potentially up to one hour)?

WHY IT MATTERS: If we detect a security incident and need to kill the ChatGPT-Jira
connection immediately, we need to know our effective incident response window. A
one-hour access token validity gap after revocation is unacceptable in a breach
scenario.

================================================================================
DOMAIN 5: JIT INSTALLATION — WHO CONTROLS THE FIRST CONSENT?
================================================================================

Q10. JIT INSTALLATION SCOPE AND ADMIN PRE-BLOCK
-------------------------------------------------
Your documentation states the Rovo MCP Server is installed just-in-time on the
first user's OAuth consent flow — it is not installed via Atlassian Marketplace
admin approval. This means a regular end user, not an admin, can trigger the JIT
installation for your entire organization by being the first to complete the OAuth
flow.

Two-part question:
(a) Is the JIT installation scoped to that user's account only, or does it register
    the MCP app for the entire org?
(b) Can a Jira org admin pre-block JIT installation until they are ready to control
    the rollout, without disabling the entire Rovo MCP Server?

WHY IT MATTERS: Standard enterprise software governance requires admin approval
before a new application can access organizational data. The JIT model inverts this
— a user action installs the app before any admin review. We need to know whether
we can gate this, or whether any user with Atlassian access can independently
trigger the integration before we are ready.

================================================================================
DOMAIN 6: BULK WRITE OPERATIONS AND GUARDRAILS
================================================================================

Q11. BULK WRITE RATE LIMITS AND OPERATION CAPS
------------------------------------------------
The Rovo MCP Server documentation explicitly mentions bulk operations: "Make five
Jira issues from these notes." There is no documented rate limit or per-instruction
write operation cap in your MCP documentation.

What is the maximum number of Jira write operations a single MCP request or
conversational turn can trigger? Is there a hard limit, a configurable limit per
org, or no limit at all? Does this limit apply per user session or per org globally?

WHY IT MATTERS: ChatGPT's natural language model can misinterpret a broad
instruction and trigger bulk writes at a scale no human user would. "Create tracking
issues for all items in this spreadsheet" on a 200-row spreadsheet could generate
200 Jira issues in seconds. We need to know whether the MCP layer provides any
guardrails against this, or whether protection is entirely dependent on whether we
have write tools disabled in Manage actions.

DOMAIN 7: DATA RESIDENCY AND CONTRACTUAL COVERAGE
================================================================================

Q12. DPA COVERAGE FOR ROVO MCP SERVER TRANSIT
-----------------------------------------------
Our Jira Cloud site is provisioned in the EU region. When Jira issue data transits
through mcp.atlassian.com, in which geographic region does that processing occur?
Does Jira issue content remain within the EU throughout the MCP server transit, or
does it route through infrastructure in other regions?

Specifically: is mcp.atlassian.com covered under our existing Atlassian DPA as a
data processor, or is the Rovo MCP Server a separate product with a separate
processing basis that requires its own DPA addendum?

WHY IT MATTERS: Under GDPR, every processing step must have a documented legal
basis and data processor agreement. The Rovo MCP Server is a new infrastructure
component that sits between Jira (covered by our DPA) and ChatGPT (covered by our
OpenAI DPA). The transit through your MCP server is a separate processing activity.
If your current DPA does not explicitly name the Rovo MCP Server as a covered
service, we have a GDPR compliance gap regardless of what the product actually does
with the data.

================================================================================
DOMAIN 8: ATTACHMENTS — SCOPE VS. TOOL VS. ACTUAL ACCESS
================================================================================

Q13. ATTACHMENT ACCESS: SCOPE COVERAGE, MISSING MCP TOOL, AND URL LEAKAGE
---------------------------------------------------------------------------
Three-part question on attachments:

(a) SCOPE: read:jira-work is documented by Atlassian as covering "objects
    associated with issues like attachments." There is also a granular scope
    read:attachment:jira. Does the current Rovo MCP connector token include
    read:attachment:jira in addition to read:jira-work, and which scope
    specifically gates the REST API endpoint GET /rest/api/3/attachment/{id}/expand
    (the endpoint that serves attachment binary content)?

(b) MISSING TOOL: The current Rovo MCP supported tools list has no
    getJiraAttachment or equivalent tool that downloads attachment content. This has
    been confirmed by the community. Is this a permanent architectural decision or a
    gap you plan to close? If it is planned, what is the roadmap timeline, and will
    existing OAuth consents automatically cover it when the tool is added — or will
    re-consent be required?

(c) URL LEAKAGE VIA getJiraIssue: The getJiraIssue MCP tool returns the full Jira
    issue object, which includes an attachments array containing the filename, MIME
    type, and direct download URL for every attached file. If ChatGPT's agent or a
    user takes that URL and sends an HTTP GET with the Bearer token in the
    Authorization header, does your infrastructure serve the attachment binary
    content? In other words: is "no MCP download tool" the same as "attachment
    content is actually blocked," or is it just that no purpose-built tool exists
    but the URL still works?

WHY IT MATTERS: If the attachment download URL returned by getJiraIssue can be
fetched directly using the OAuth token — which read:jira-work already permits at
the scope level — then attachment binary content is effectively accessible today
through ChatGPT's agent browsing capability, even without a dedicated MCP tool.
We need to know the actual enforcement boundary, not the documented tool list.
